Predictions & Scoring

From executed actions to checker judgments and TR / JR.

SJTU-DeepVisionLab/RoboInFv1.0.0

A run produces predictions (the executed actions). A checker turns each rollout into a judgment, and roboinf score aggregates judgments into TR and JR.

Predictions

roboinf run writes one JSONL row per completed case with these fields:

FieldContent
case_id, task, domainWhich case was evaluated, and under which domain
policy, policy_seedPolicy interface and the fixed policy RNG seed
action_specjoint14_absolute or eef16_absolute_wxyz
action_count, actionsNumber of actions and the ordered list of executed actions

A one-case installation check is not a full benchmark result.

Judgments

Official judgments require replay or equivalent simulator evidence for the policy's own rollout. Expert demonstration labels must never be reused to score a new policy. A checker export has exactly these fields per case (illustrative values):

{"case_id":"example","domain":"val","task_success":true,"instruction_success":false}

The task-specific checker conditions behind task_success and instruction_success are listed on each task page under “Fidelity checker”.

Score

roboinf score --data ./RoboInF-4K --domain val --judgments val-judgments.jsonl

The command prints per-task cases, TR and JR, and the benchmark averages macro_TR and macro_JR.

Task success (TR)task_success is true.
Joint success (JR)Both task_success and instruction_success are true.
  • A task's rate is the fraction of successful cases. The benchmark average gives equal weight to each of the eight tasks, separately for validation, clear test and appearance-randomized test.
  • Exactly one judgment per case is required. Unknown, duplicate and missing cases are rejected rather than changing the denominator, so dropouts and infrastructure errors must be resolved first.
  • The command aggregates evaluator judgments; it does not infer physical success from action arrays.

Held-out test

The hidden test checker and the individual official test judgments are not distributed, and the repository does not host a scoring service. Comparisons with paper results additionally require matching simulator dependencies, assets, dynamics, rendering and policy settings; matching the scene seed alone does not verify the full initial state.
